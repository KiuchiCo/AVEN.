## Calendar sync: how it stays up to date

Connected calendars sync **by themselves**; "Sync now" on the Connected apps card is only a shortcut.

- **When it runs.** (1) Right after connecting or reconnecting. (2) In the background: a check runs every minute (and once 20 seconds after the API starts, so a restart never leaves a calendar waiting) and syncs each active connection whose last sync finished about five minutes ago. Only connections whose connector is still an owner or administrator are synced, and a disconnected account is gone from the table, so nothing touches it. (3) While anyone has the Calendar page on screen: `POST /workspaces/:id/integrations/calendar/refresh` every 10 seconds (and straight away when they open the page or return to the tab) syncs connections that were last synced more than 8 seconds ago, so several tabs or people never multiply the requests. A quiet account costs one small incremental request to Google about every 10 seconds, only while a calendar page is open; nothing runs from a hidden tab. (4) About a second after an event is created, edited or deleted in AVEN, connections that receive AVEN events are synced so the change reaches the calendar promptly. Guests do not trigger (3) or (4); the background run covers them.
- **Incremental sync (Google).** The first read takes the whole window (the last 30 days and the next 180). Google returns a *sync token*, kept in the connection, and later syncs ask only for what changed since: new events, edits, and cancellations (deletions). Every six hours, and whenever the token is rejected (Google answers 410), the whole window is read again, which also picks up events that have moved into the window. The token only moves forward when every change was applied, so a partly failed sync is repeated safely. Recurring events are read as their individual occurrences (`singleEvents`), at the right instant for any time zone; AVEN's own repeating events are not sent to Google.
- **Two-way, without loops or duplicates.** Each AVEN event and its provider copy are paired by a stored link, never matched by text. A change AVEN sends comes back from Google with the etag AVEN already stored, so it is not treated as a new change. If both sides changed, the later edit wins and the activity feed says so. An AVEN event goes to one connected calendar only.
- **Failures.** Expired access tokens are refreshed; revoked permission or a token that lacks the calendar permission marks the connection "needs to be reconnected". Rate limits, outages and timeouts retry with a growing delay (5, 10, 20, 40 minutes, then hourly) and after eight failures in a row background syncing stops and the card asks to reconnect. Nothing retries in a tight loop, and a single failing event does not stop the others.
- **The card.** Shows the account, status, last successful sync, "Syncing now…" while one runs, the last error if there is one, Disconnect, and Sync now. It refreshes itself (every 3 seconds while syncing, otherwise every 15) without a page reload.
- **Setting.** `CALENDAR_SYNC_DISABLED=true` turns the background run and the automatic sends off on a server (it is always off in tests). Opening the calendar and the manual button still work.

**The calendar page stays live.** The page asks `GET /workspaces/:id/events/revision` (one small aggregate query: how many events, and when the newest change happened) every 5 seconds while the tab is on screen, and straight away when you return to it. Only when the answer changes does it reload the events (not tasks or projects), so a background sync, another tab or another person's edit shows up within about 5 seconds without touching the page. Measured on a real Google account: an event made in Google appeared in the open calendar in about 6 seconds, and a deletion in about 8. The selected date, view and filters belong to the page and are never reset. After the page's own create, edit or delete it records the new revision itself, so it does not load twice. If the revision check fails the calendar still loads. An unchanged calendar costs about 18 tiny requests a minute while it is open.

**Sending AVEN events to Google (needs "Also send events made in AVEN" on).** The setting is per connection and is kept when you reconnect. Turning it on asks first, and says how many existing events (non-repeating, from 30 days ago to 6 months ahead) will be added once. There is no separate queue: a change is "pending" while the links don't match it yet (a new event with no link, an edit newer than its link, or a deletion whose link remains), so the card can say "N changes waiting to be sent", a sync that works clears it, and one that fails leaves it for the next try (the scheduled run, at most about 5 minutes later). Events are saved in AVEN first and never lost to a Google failure.
- *Created once.* The Google copy gets an id derived from the connection and the AVEN event (`avn` + 40 hex digits), so a retry after a lost answer finds that copy (Google answers 409 for a repeated id) instead of making a second one, and a copy found in the next read is paired with its AVEN event instead of being imported as a new one.
- *Edits.* Sent with the stored etag; a Google edit made at the same time is reported as a conflict and the later edit wins.
- *Deletions.* Deleting in AVEN keeps the link (without its event) until Google confirms; the Google event is identified only by that stored id, so an event AVEN never sent is never deleted, and an unsent event deleted before any sync makes no Google request. While the link remains the event is not re-imported.
- *No loops.* A change that came from Google is stored with Google's etag and the AVEN time it was copied, so it is not sent back; AVEN's own change returns with the etag AVEN stored, so it is not treated as new.
- *Limits.* A change that Google permanently refuses is retried at every scheduled run (about every 5 minutes) while it stays pending, and shows on the card. Repeating AVEN events are not sent.

**Google quota.** Calendar API quota is per project and generous for this use (a quiet account costs one small request per sync: about 12 an hour from the schedule, plus about 360 an hour for each calendar page left open, since an open page syncs every 10 seconds; the full read every six hours pages 250 events per request). With many connected accounts, keep an eye on the Calendar API quota page in Google Cloud and raise `DUE_AFTER_MS` and `OPEN_COOLDOWN_MS` (in `calendar-sync.service.ts`) and the 10-second interval in `connected-records.tsx` if needed. Google push notifications (below) would replace the 10-second polling with an instant call-back.

**Google push notifications (not enabled).** Google can call AVEN the moment an event changes (the `events.watch` API) instead of waiting for the next check. It needs a public HTTPS address for the API, so it is not switched on for localhost. To add it in production: register a channel per connection after it connects (address `<API_PUBLIC_URL>/api/v1/integrations/calendar/google-notifications`, a random channel id and secret token stored with the connection), accept the notification on a public endpoint that checks the channel id and token, and respond by calling `CalendarSyncService.syncConnection(id)`, which already does an incremental read. Channels expire (at most about a week), so renew them from the existing runner, and stop the channel when a connection is disconnected. The one-minute check should stay as the backstop. None of this is built; the sync service is already shaped so it can be added without changing the integration.

**OAuth requirements.** Scopes `openid email https://www.googleapis.com/auth/calendar.events`; the Google Calendar API enabled in the project; the redirect address `<API_PUBLIC_URL>/api/v1/integrations/calendar/callback`; `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `TOKEN_ENCRYPTION_KEY`. Tokens are stored encrypted and never sent to the browser. On Google's screen the person must leave the calendar permission ticked; otherwise AVEN refuses the connection instead of saving a broken one.

All of this is tested against a local stand-in for Google's calendar API (sync tokens, expiry, cancellations, failures, quota-style errors). No real Google account was used.
